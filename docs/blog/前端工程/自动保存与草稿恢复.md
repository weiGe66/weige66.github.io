在一个自部署学习工作台的 Markdown 编辑器里，停下来两秒会触发自动保存。最容易漏测的是这个顺序：新笔记已写入数据库，浏览器却收到了故障代理返回的 503。用户刷新后如果用一个新请求重试，可能多出一篇笔记。如果用户又写了一段，补到的成功响应也可能把新输入盖掉。

## 分开处理正在编辑、已提交和已确认的内容

| 数据 | 持有内容 | 什么时候改变 |
| --- | --- | --- |
| 当前草稿 | 表单正在显示的内容 | 用户输入、恢复草稿或明确选择合并时 |
| 待确认操作 | 提交时的内容快照、笔记标识、基线 revision、操作键 | 发起一轮新保存时创建，重试沿用这一份 |
| 服务端基线 | 最近一次确认的内容与 revision | 确认保存成功，或用户明确采用服务端版本时 |

同一编辑器串行提交，防抖只决定什么时候发起保存。有响应时更新基线，再对比当前草稿是否仍等于提交快照。只有内容未继续修改，才把服务端归一化后的字段写回表单。对于只读查询，页面可以直接丢弃过时的结果，相关时序见 [搜索框请求竞态](./搜索框请求竞态.md)。

下面单用正文字段演示，实际项目还一起比较了标题、分类和标签。

```js
function applySaveAck(editor, ack) {
  const { pending } = editor
  if (!pending || pending.key !== ack.key) return editor

  return {
    ...editor,
    noteId: ack.noteId,
    baseline: { body: ack.body, revision: ack.revision },
    body: editor.body === pending.body ? ack.body : editor.body,
    pending: null,
  }
}

const editor = {
  noteId: null,
  body: '第一段\n第二段',
  baseline: { body: '', revision: 0 },
  pending: { key: 'save-1', body: '第一段' },
}
const saved = applySaveAck(editor, {
  key: 'save-1',
  noteId: 42,
  revision: 1,
  body: '第一段',
})
if (saved.body !== editor.body || saved.baseline.revision !== 1) {
  throw new Error('保存响应覆盖了新输入，或基线没有更新')
}
```

这里的 `ack.key` 由客户端把响应与原请求关联。当前草稿仍比基线多一段，下一轮应基于 revision 1 提交这段内容。把代码保存成 `autosave.mjs` 后可以直接用 Node.js 运行。

## 刷新后先确认上一笔写入

工作台在本地草稿里同时保存最后的表单内容与待确认操作，按账户和笔记定位记录。IndexedDB 事务提交后才显示「本浏览器草稿已备份」。如果备份失败，页面提示另存；如果服务端已给新笔记分配 ID，就在同一个事务里迁移草稿键，避免旧的「新建」记录继续出现。[MDN · IndexedDB 事务的 complete 事件](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction/complete_event)

恢复顺序决定是否会重复写入。

1. 用原操作键、原 revision 和原请求体重试。一个操作键绑定一份载荷，服务端先查已成功的操作，再做版本检查。首次成功时，在同一个事务里提交业务变更和重放记录。
2. 重试确认后重新读取服务器。如果第一次保存成功之后又有人修改过笔记，界面进入冲突处理，供用户比较本地和服务器内容。
3. 只有原操作已确认，且当前输入仍需要保存时，才创建新操作键。单独改写请求体后沿用旧键会混淆两次写入。

版本检查也可以由 HTTP 条件写入实现，例如用强 ETag 和 `If-Match` 防止覆盖新版本。条件写入解决并发修改，重放记录解决「同一笔写入到底成没成功」。工作台使用的是请求体里的 revision 和业务冲突响应。[MDN · If-Match](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/If-Match)

## 如何验收

| 注入场景 | 要检查的结果 |
| --- | --- |
| 延迟成功响应，等待期间继续输入 | 基线前进，编辑器保留第二段，有后续保存 |
| 服务器已提交，故障代理丢弃成功响应，再刷新 | 待确认操作可以恢复，使用原键重试，列表只新增一篇 |
| 两个标签页从同一 revision 修改同篇笔记 | 后提交的一侧保留本地输入并展示冲突，服务器保留已保存内容 |
| 本地存储拒绝写入 | 仍可编辑，明确显示备份失败，给出复制另存路径 |

前三项在项目当时的本地浏览器验收中通过。第四项是应补的故障注入用例，原记录没有覆盖 IndexedDB 配额耗尽。只看「已保存」提示，很难确认重复记录和被覆盖的输入有没有发生，验收时应同时核对页面内容、请求记录和服务器最终数据。
