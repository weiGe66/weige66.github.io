任务看板的原子排序，拖拽之后还要做什么

1118 字约 4 分钟

前端工程Vue可访问性

2026-11-23

学习工作台的任务有待办、进行中和已完成三列。把卡片拖到已完成列，会同时改变卡片位置、任务状态和完成时间，还会影响仪表盘。拖拽库知道卡片放在哪里，状态写入是否完整、另一页是否改过任务，以及失败时焦点回到哪里，需要页面和接口一起约定。

把跨列移动当成一次提交

在同一列内排序，只需更新该列。跨列移动则涉及源列和目标列，源列被移空也应明确提交。接口接收完整的受影响列，每项带读取时的版本，数组顺序就是新顺序。

例如原顺序为待办 [A, B]、已完成 [C]。把 B 放到 C 前，提交如下结构。示例把 A、B、C 编号为 101、102、103。

[
  {
    "status": "todo",
    "tasks": [{ "id": 101, "base_version": 3 }]
  },
  {
    "status": "done",
    "tasks": [
      { "id": 102, "base_version": 7 },
      { "id": 103, "base_version": 2 }
    ]
  }
]

服务端在同一个事务里校验并更新这两列。先比较任务集合，能发现另一页新建或移走了卡片。再比较每项版本，能发现任务集合相同期间的状态和顺序变更。任一检查失败，整次排序拒绝。成功时把状态、顺序和相关完成记录一起提交。

筛选会改变用户看到的数据

以待办 [A, B, C] 为例，筛选后只显示 [A, C]。将 C 移到 A 前时，B 应留在什么位置，需要额外的产品定义。如果把可见列表直接当整列提交，还可能把 B 从结果中遗漏。

当时的取舍是只在完整看板开放排序，筛选后仍可通过状态下拉逐项移动。这个方案的代价是用户要先清除筛选才能调顺序。对于每列很长、只能分页加载的看板，可以设计基于相邻卡片的移动指令，由服务端校验锚点和版本，再计算排序值。

回滚时同时恢复界面和操作位置

写入结果看板如何处理
服务端确认成功读取最新任务和进度，显示服务端接受的顺序
连接中断，结果未知恢复拖前快照并提示重试。用原操作键和原载荷确认，服务器可能已经提交
明确返回版本或集合冲突读取新看板，让用户基于新顺序重新操作

恢复拖前快照只影响页面显示，服务端是否写入要看后续确认结果。原操作键的恢复方式也适用于编辑器自动保存。

项目同时提供向前、向后按钮和状态下拉。排序按钮与拖拽复用排序流程，状态下拉通过同一套任务更新流程处理。操作前记录任务 ID 和控件动作，等提交结束且 DOM 更新后，如果焦点意外落到 body，再定位到同一卡片的同一控件。若用户已 Tab 到别处，保留他当前位置。卡片已被当前筛选移除时，可以回到搜索入口这样的稳定控件。可点击的按钮同时提供了无需拖动的指针操作路径。W3C · Dragging Movements

用两页和一次断线检查

  1. A 页保持原看板，B 页在目标列增加任务。A 页再执行跨列移动，应收到冲突，源列和目标列都没有部分写入。
  2. 中断排序请求，检查界面回到拖前顺序，恢复连接后重试原操作，核对最终顺序和已完成任务数。
  3. 全程用键盘完成、撤销、同列移动和跨列切换，检查焦点能持续留在相应控件。再在请求中途把焦点移开，观察返回时是否被抢回。

项目当时用接口测试覆盖了缺项和版本冲突的整笔回滚，并在本地浏览器验证了实际拖拽、失败回滚、键盘重试和焦点恢复。手机视口与键盘路径已有记录，触屏拖拽和辅助技术兼容性仍需按目标设备验证。
