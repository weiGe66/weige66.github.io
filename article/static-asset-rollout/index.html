发布后旧页面为什么会加载失败：从缓存到回滚

1318 字约 4 分钟

前端工程发布

2026-11-23

A 版页面已经打开。用户在标签页停留期间，站点发布了 B 版，并删除 A 版的资源。用户随后第一次打开详情页，运行中的 A 版 JavaScript 仍会请求 detail.a123.js。资源返回 404，路由切换失败，而新开标签页通过 B 版 HTML 加载 B 版资源，表现正常。Vite · Load Error Handling

这个问题能用两个标签页复现。它也说明 HTML 的缓存验证和旧资源保留分别作用于新打开的页面和已经在运行的页面。

从实际请求判断是哪一层出了问题

打开浏览器 Network 面板并保留记录，保留出现故障的标签页。先记下失败的 URL、状态码、响应类型和请求的 Initiator。然后在另一个标签页打开同一路由，对照两边请求的入口文件版本。

观察结果下一项检查
旧标签页请求旧哈希，返回 404查发布时是否清理了上一版产物，以及边缘节点是否仍有对应资源
新标签页拿到旧 HTML 或旧入口脚本查 HTML 的回源验证、CDN 缓存配置，以及 Service Worker 的导航响应
.js 返回 200，响应内容是 HTML查静态资源路径是否被 SPA 回退规则接管
新旧标签页都请求到同一个错误前缀查构建配置中的 base 和站点部署目录

浏览器可能命中本地缓存。复现旧 chunk 缺失时，从来没有访问过对应懒加载路由的旧标签页开始。比对响应头时，可以额外请求实际对用户提供服务的域名，核对状态、Content-Type、Cache-Control 和 CDN 的缓存状态。

为入口和带哈希资源分别设置缓存策略

资源常见策略前提
页面 HTMLCache-Control: no-cache再用时向服务器验证新鲜度，可配合 ETag 返回 304
带内容哈希的 JS、CSS 和图片Cache-Control: public, max-age=31536000, immutable同一 URL 的内容保持稳定，内容变化生成新 URL
可选的版本清单 /version.jsonCache-Control: no-cache发布切换时同步更新，客户端可用它判断当前会话是否落在旧版本

no-cache 允许保存响应，复用前需要验证。采用同名文件覆盖时，长缓存会让不同用户运行不同内容，应先建立稳定的资源版本规则。Service Worker 有独立的缓存策略，部署使用它的站点时也要检查导航请求如何取版本。MDN · HTTP 缓存

发布顺序决定回滚是否可用

团队可以配置对象存储、CDN 或静态服务器时，可以按下列顺序发布。

  1. 先上传新版本的哈希资源，并验证用户访问域名上能成功获取它们。
  2. 再切换 HTML 和版本清单。如果托管支持原子切换，就一起切换。分步更新时，让版本清单最后发布，避免客户端先收到更新信号。
  3. 保留上一版及回滚窗口内需要的完整资源。回滚要切换对应的 HTML 和版本清单，并确认它们引用的资源仍然可取。
  4. 结合会话时长和旧哈希资源的请求量决定保留周期。对于长时间打开的工作台，固定保留最近一版可能撑不过一次密集发布。

版本轮询可以提示用户更新，也可以在加载出错后为客服或日志补充版本信息。表单和编辑器有未保存内容时，应让用户确认刷新或先保存草稿。网络暂时中断也可能导致动态导入失败，恢复逻辑需要区分断网与版本切换，刷新次数应有限制。

本博客把产物发布到 gh-pages，工作流启用了 clean: true。上面的缓存头和旧资源保留面向可配置的托管环境，GitHub Pages 的实际响应头以线上请求为准。博客发布工作流

用两个版本验证

  1. 发布 A，打开一个标签页，停留在入口页。
  2. 发布 B，让某个懒加载路由的输出发生变化。新标签页打开入口和目标路由，核对使用的资源版本和响应类型。
  3. 在 A 的标签页首次进入该路由。验证 A 的 chunk 仍然可用，或应用能给出可恢复的提示并照顾未保存内容。
  4. 模拟回滚到 A。重新打开标签页，检查入口、路由和失败资源的响应，再核对版本清单。缺失的 JS 请求应返回资源错误，避免被 HTML 回退伪装成成功。
